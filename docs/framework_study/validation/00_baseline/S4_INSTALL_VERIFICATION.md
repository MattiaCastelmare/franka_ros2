**O-14 (new observation): the install copies the source tree's gitignored `__pycache__`.**
`franka_simulation/CMakeLists.txt` L144 installs `scripts/utils` as a whole directory, so the 26 cache
files in `franka_simulation/scripts/utils/__pycache__/` (written by earlier runs on the host and in
the container, 2026-02-09 … 11-06) are copied to `install/franka_simulation/lib/franka_simulation/utils/__pycache__/`.
Consequences, checked:
- 22 are `cpython-313` (host Python): CPython 3.10 never reads them (tag mismatch).
- 4 are `cpython-310`. For `gz_world` the header does not match the installed `.py`, so it is ignored.
  For `__init__`, `gz_robot_description` and `depth_conversion` the header matches, so CPython 3.10
  **would load them**; their code objects are equal to a fresh compile of the installed `.py`
  (co_filename aside). **No stale bytecode is used today** (Verified).
- The real defect is reproducibility: the content of the install depends on untracked files in the
  working tree, not only on the commit. No other copied artifact exists in the six packages
  (`franka_experiments`' `setup.py` copies listed files only). It is a code-level install-rule defect,
  recorded as an observation like O-1…O-13; whether it gets a finding ID is the user's decision.

In every context the four pipeline node modules (`cbf_safety_filter`, `real_time_distance`,
`qddot_to_torque`, `pentagon_qddot_commander`) import, and every loaded module under `/ros2_ws` (56)
is either an S3-built install file (all of which equal the baseline, §3) or a tracked, unmodified source
file. Nothing loads from the quarantine, from an untracked file or from a copied `.pyc`. The
`franka_msgs` types used by the in-scope Python load from the new install. Verified.

- **F-7-5 after the rebuild:** the mechanism is unchanged (only `python -c`/`-m` from
  `src/franka_experiments` picks the source), but its consequence is gone **while install == source**:
  both resolve to byte-identical baseline files. It returns as soon as a source file is edited
  without a rebuild.
- **O-9 refined:** the trailing `:` of `PYTHONPATH` puts the cwd at `sys.path` index 10, **after**
  every install and ROS entry and **before** the standard library. It therefore never overrides an
  installed package (a node wrapper started from `src/franka_experiments` still imports the install),
  but it can supply modules that are not installed and could shadow a standard-library module of the
  same name. The S2 wording ("makes the import source depend on the cwd together with F-7-5") is
  corrected: the cwd dependence of F-7-5 comes from `sys.path[0]` of `-c`/`-m`, not from O-9.
- **O-15 (new observation):** `fr3_student_sim` (tracked on `humble-mattia`, outside the study scope,
  installed by an older symlink build of another branch's tree) puts `/ros2_ws/build/fr3_student_sim`
  at `sys.path` index 3, before `franka_msgs` and `/opt/ros`. It provides the top-level names `config`,
  `launch`, `fr3_student_sim`, `resource`, `share`, `students` as namespace portions. Checked: `launch`
  still resolves to `/opt/ros/humble` (a regular package beats a namespace portion) and no in-scope
  file imports `config` or the others, so no in-scope import is shadowed (Verified). It is a latent
  hazard for any future top-level module with one of those names.
